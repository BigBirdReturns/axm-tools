SCHISM / OPERATOR GUIDE

Your applications. Your authority.

Package declared work, run it on your machines and retain a verifiable history.

Return to console

Run an application

Import a .schism package from Packages. Inspect its command, publisher fingerprint and data contract. Authorize a new publisher for the application's id, then deploy the selected release. Deployment starts a service; a task waits for you to select Run task.

The Applications panel shows observed process state and the persistent data directory. Activity retains each job, its combined output, result and errors. Closing the console leaves detached workers and services running. Stop or Cancel controls them explicitly.

Package your own work

Create schism.json beside the files you intend to distribute. The command is an argument array. The recipient supplies its declared interpreter and other executable prerequisites.

{
  "schema": "schism.application/v1",
  "id": "my-app",
  "name": "My application",
  "version": "1.0.0",
  "kind": "task",
  "command": ["{python}", "app.py", "{data}/input.csv"],
  "environment": {},
  "secret_env": [],
  "data_schema": "1",
  "task_timeout": 300
}

Use the quoted command prefix printed by the launcher, including its chosen state. Source commands below use python schism.py; standalone controllers use ./schism or .\schism.exe. The Python examples require an installed Python interpreter even with a standalone controller:

python schism.py pack /path/to/my-app --output /path/to/my-app.schism

{release} locates retained code, {data} locates persistent application data, and {work} locates the individual run directory. The same locations are available through SCHISM_RELEASE, SCHISM_DATA and SCHISM_WORK. Keep private keys, credentials and the output package outside the source directory.

The console and SSH transport accept archives up to 64 MiB. Larger valid archives, up to the local 256 MiB limit, can be copied separately and imported through the local CLI. Payloads have a 512 MiB total, 128 MiB per file and 10,000-file bound.

Use your own data

The included csv-summary example processes recipient-supplied UTF-8 CSV with an optional byte-order mark, comma delimiter and header row. Package and deploy it, put your file at input.csv in its displayed data directory, then Run task. Its output is summary.json. The application reports missing input as a failed job.

python schism.py pack examples/csv-summary --output csv-summary.schism

Update and recover

Import a new version with the same application id. Deploy it from the package inspector. A service update stops the selected process, starts the candidate and checks its declared health before committing the new generation. A failed candidate triggers an attempt to restart the prior authorized release. The prior version remains available after a successful update.

Restore prior version changes the code and retains current data. Both versions must declare the same data_schema. An application-specific migration owns any actual data-format change. Recover observes retained process identities and stops uncommitted candidates; it never automatically replays an uncertain task.

Private runtime configuration

Declare required secret names through secret_env. The package inspector and application settings accept recipient-local environment values before a service starts. Saving replaces the configured set. Future starts receive those values; already-running processes retain their previous environment.

Move to a replacement operator

Stop an application before creating a consistent backup. Its backup contains selected/prior packages and persistent data; it excludes private signing keys, local runtime configuration, logs and process state.

python schism.py stop my-app --expect 3
python schism.py backup my-app --output my-app-backup.zip
python schism.py identity

python schism.py --state /new/state restore my-app-backup.zip --key-id SIGNER_FINGERPRINT

Establish the backup signer's fingerprint through an independently trusted channel. A replacement recipient restores into an unused application id, authorizes the publisher, supplies its own runtime configuration and starts the application under its own identity.

Connect independent nodes

Install SCHISM and its dependencies on a POSIX SSH recipient. Configure ordinary OpenSSH authentication and a known-host pin through your normal system administration. SCHISM uses that existing account with batch authentication and strict host-key checking; it does not copy credentials or expose a remote control server.

python schism.py node add workstation \
  --host your-ssh-alias \
  --python /home/me/schism-runtime/bin/python \
  --root /home/me/schism-stack \
  --remote-state /home/me/.schism
python schism.py node status workstation
python schism.py node import workstation my-app.schism
python schism.py node action workstation request.json
python schism.py node job workstation JOB_ID

Lifecycle requests use the same API shape, for example {"operation":"deploy","release_id":"…","expected_generation":0,"request_id":"deployment-001"}. The recipient separately authorizes publishers for explicit application ids. The console displays registered peers and their observed snapshots; its application controls operate locally.

Export independently verifiable evidence

Export evidence downloads signed release metadata, signed sequential events, observed application selection and job identity/status. Runtime override values, logs, application data and private keys remain outside this export.

python schism.py verify-evidence evidence.zip --key-id OPERATOR_FINGERPRINT

A signature establishes consistency with a key. An independently known fingerprint establishes which operator's record you accept. Application correctness, physical hardware identity and external approval retain their own acceptance requirements. Managed packages execute as trusted code under the recipient's OS account.
