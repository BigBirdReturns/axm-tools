# SCHISM 2.0: executable continuity after supplier substitution

Jonathan Sandhu · 27 November 2026

## The result

This release adds an independent Python implementation to an existing JavaScript calculation and custody contract. A recipient reconstructs all historical conclusions, accepts a pending source correction, computes a new conclusion and returns a capsule that the original JavaScript implementation can accept. The source workspace can disappear because the handoff contains the records and dependency history required for that work. The program states a specific refusal when the retained evidence or interpretation is incomplete or inconsistent.

The browser application performs the exit drill live in JavaScript. The separately retained Linux and Windows receipts concern execution of the delivered Python implementation in fresh native processes. The original JavaScript receiver supplies the final return-path check. `data/qualification.json` distinguishes these records and binds them to the actual Python source hash. The online surface does not claim to execute Python.

## What changed since June

The June dossier asked whether a customer could retain useful control across a supplier change. It identified distinct dependencies around execution, trusted changes, communication, maintenance and evidence. Those categories matter because access to one layer does not automatically carry the history, interpretation or rights needed at the next. The central question was an operating test: what remains executable when a particular organization stops supplying a service?

The first public edition reduced that question to a responsibility taxonomy. Edition 2.0 supplies an executable software case. It preserves the existing Industrial Continuity contract, introduces a separately written implementation, makes pending work explicit, and records a recipient continuing it outside the originating application. This is a completed bounded experiment in replaceable software interpretation and retained customer work.

The broader November estate supplies useful surrounding evidence. Industrial Continuity already preserves six source families, revisions, calculations and reviews. Cantos already carries captured compute observations through independent analysis and reuse while retaining failed qualification. Decision Floor already exchanges scoped signed statements between separately held vaults and retains disagreement. Genesis already seals and verifies content bytes and refuses modified leaves. These components retain their own owners, schemas and qualification boundaries. This edition directly executes the industrial contract and the included Cantos recipient path; it cites Decision Floor and Genesis as separately established mechanisms rather than claiming a newly integrated protocol among them.

The Python calculation uses integer cents. For each feasible quantity of product A it derives the greatest feasible quantity of B under the two resource bounds. Positive resource requirements and nonnegative contribution make that choice sufficient for the fixed-A objective; zero-contribution ties still prefer the larger unit count. Iteration and final option ranking preserve the donor's remaining tie behavior. The qualification suite compares the implementation with both the original JavaScript calculation and a separate exhaustive feasible-set oracle.

The receiver reconstructs the source history and verifies that every decision uses a possible, nonregressing frontier. It recomputes all historical results, including their alternative plans and explanatory fields. A current result cannot conceal a changed or fabricated earlier saved conclusion.

The receiver admits UTF-8 JSON with unique members and safe integer-valued numbers. Timestamps use calendar-valid, timezone-qualified ISO syntax with seconds. The original JavaScript runtime accepts some additional Date.parse spellings; Python explicitly refuses those spellings. This receiving profile avoids silently inventing equivalent dates. The finite qualification includes Unicode canonical ordering and escaping, line-ending retention, timestamp conversion, monetary bounds and ties.

## The exit drill

The synthetic original record supports a plan of A80/B35 and modeled net contribution of 565,000 cents. A retained reviewer label refers to that exact decision. Changing product B's contribution from 40 to 120 dollars creates a new source revision. Before any recalculation, the existing decision becomes stale and its review loses current standing.

The producer exports that unfinished record, then closes its workspace. The recipient uses the capsule to reconstruct the earlier calculation and identify the pending frontier. A separate continuation computes A30/B60 and 885,000 modeled net cents within the original capacity. The earlier decision and review remain retained, and the review remains stale until a separate review of the new decision. Repeating continuation on an already current record adds no duplicate decision.

The 320,000-cent difference is a changed synthetic economic assumption. It is not measured factory improvement or revenue attributable to AXM. The demonstrated property is preservation of the exact reasoning record and correct continuation under the changed inputs.

The pending capsule's identity is `db6282c3972e177aaaf80b86e6f42b27984d580f9297a715cb3d7421ceb9f53a`. Python continuation must produce `0e50f98690eb4632c6c4751f419af90ed2c0425e3d8303738ab99e0fdcba0f4c`, matching the independently generated JavaScript result. The original JavaScript receiver then verifies the Python-authored capsule, including its complete history.

## Refusals are part of the result

The browser exposes five modified handoffs: changed source bytes, an altered saved conclusion with correctly recomputed hashes, a missing retained dependency, invented operational authority, and a different engine identity. Each candidate passes through the real importer. A refused candidate preserves the previously accepted receiver state. Additional native tests exercise orphaned and forked revisions, regressing observation times and frontiers, invalid historical sequence numbers, incompatible review roles and unsupported numerical or timestamp representations.

Origin-service loss and evidence loss are different cases. An intact exported record can remain usable after the source application closes. A record missing required retained dependencies cannot supply a supported conclusion. Similarly, a hash-consistent false saved result must fail independent recomputation even though its byte-level checks pass. A self-consistent invented source history remains outside what these checks can authenticate.

Review labels remain declared, unverified labels. The record and every accepted calculation preserve `operational_authority:false`; a source consistency result grants no permission to act on equipment or an enterprise system. The examples perform local arithmetic and state changes only.

## Reproducibility and interpretation

`run.py` verifies the complete delivered source set before spawning a fresh Python receiver for every positive and negative handoff. It denies the ordinary Python socket APIs. With `--with-node`, the final JavaScript acceptance process also denies HTTP, TLS, socket and fetch APIs. The receipts record invocation attempts under those guards. They establish the delivered program's tested offline execution; the guards are test instrumentation rather than an operating-system sandbox for arbitrary hostile code.

The public release manifest identifies every shipped file. A selected expected manifest can identify a modified executable or missing source. An externally retained artifact digest or pinned Git commit supplies the comparison point. A program reporting its own hash does not authenticate its author, and possession of a manifest does not establish physical truth. The release makes these boundaries explicit instead of treating a large pass count as universal assurance.

`data/native-source-binding.json` binds the two retained native receipts to the runtime and fixture bytes extracted from their checksum-verified candidate archive. The page builder marks those receipts stale if those inputs change. The packet and execution-receipt files use individually exclusive creation; their two-file publication is not an atomic transaction. A packet left without its receipt after an interrupted write remains an incomplete execution record.

The software result concerns this declared two-product, two-stage calculation contract and its retained evidence. Hardware substitution, boot firmware, radio behavior, physical recovery, real organizational identity and the behavior of any Darkhive deployment require their own evidence. This package does not establish those properties. Its completed contribution is narrower and executable: a customer-held record remains independently interpretable, a replacement implementation can continue its work, and unsupported conclusions remain refused.
