First test: delayed or missing camera frames

Start with what your setup already records. A short video or frame sequence, its timing metadata, and a matching native flight log if one exists are enough to inspect the first event. For a Pi-and-camera bench test, camera data alone is a useful start. Include the hardware/firmware versions and one sentence about what the controller should notice or do.

A 30–60 second sample around the event is a useful starting size. These templates are optional interchange examples, not a requirement to change your stack.

Record when availableWhat it tells us

Camera timestamp + clock IDWhen the source says the image was acquired, in its own clock domain.
Pi reception timeWhen the capture application first received the frame.
Controller consumption timeWhen perception or control actually used it, on the same Pi monotonic clock.
Status + image referenceWhat was observed and which image or video frame it belongs to.

Leave unknown fields blank. Keep original clocks: subtract Pi reception from Pi consumption to measure queue delay; compare a camera clock with a Pi clock only with a measured mapping. Sequence gaps establish missing entries, not where the loss occurred.

Controller decisions and flight-controller telemetry
Keep native .ulg, .tlog or equivalent logs intact. Preserve the autopilot’s clock and host-receipt times where available. An optional decision log connects each output to the last frame used. A bench-only capture can simply state that no flight controller or control output was involved.


Choose the first event and expected response together. The same recorded case can then become a repeatable test as the controller changes. Exchange source logs through your existing private channel; this page does not upload data.

Source identity and limits
The receipt retains sampled trace values and the original full-ledger digest; the full original ledgers were temporary and are not embedded here. The run’s hash chain is distinct from a signed Genesis shard. Reproduction from source needs the matching axm-embodied checkout.


Connecting a Pi and flight controller
The existing external-controller interface uses TCP JSONL. A separate MAVLink / pymavlink path has been exercised against PX4 in software simulation. The camera’s capture API, frame metadata and the board’s firmware determine the hardware adapter. Existing autopilot and companion-computer conventions remain underneath it.


This page is the demo and format reference. It opens no connection to a Pi, flight controller or aircraft.
